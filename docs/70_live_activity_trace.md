# 70. v4.5.7：实时阶段轨迹与“未发现车辆”误显示修复

版本：`4.5.7-min / versionCode 507`。

## 1. 现象

用户打开 App 后靠近车辆，顶部长时间显示“未发现车辆”，随后车辆直接解锁。实际过程中 App 已经经历了：

```text
广播发现 → 唤醒银河 → ACL 建立 → V2 鉴权 → 官方通知就绪 → 创建解锁请求 → 发送官方 PI
```

但旧界面的顶部状态只读取“当前瞬时值”，主页面每 `500 ms` 拉取一次服务快照；这些阶段很多只持续几十毫秒到几百毫秒，因此可能在两次 UI 刷新之间被后一阶段覆盖。

## 2. 修复

新增 `LiveActivityTrace`，服务每进入关键阶段就立即追加一条带单调时间的事件：

- `SCAN_FOUND`：发现本车广播；
- `WAKE_REQUEST`：已把真实 `ScanResult` 交给银河 `MiuiService`；
- `ACL_CONNECTED`：车机底层链路建立；
- `OFFICIAL_CONNECTED`：银河通知/鉴权就绪；
- `UNLOCK_REQUESTED` / `LOCK_REQUESTED`：形成待发请求；
- `UNLOCK_SENT` / `LOCK_SENT`：通知 PI 已交付；
- `RESULT_UNKNOWN`：官方发送结果未知；
- `SCAN_LOST`：广播失效（用于区分“等待”和“刚发现后消失”）。

顶部实时行为条现在优先显示最近轨迹，并在详情下追加：

```text
最近：发现 → 唤醒 → 链路 → 鉴权 → 已发送
```

轨迹最多保留 8 条，界面显示最近 4 步；旧的短阶段超过 30 秒后不会继续冒充当前动作。

## 3. “未发现车辆”的具体原因

首次广播用来唤醒银河时，还只是“连接资格”，并不一定是可信 RSSI 样本。旧 UI 只有在 `lastSampleAtMs / Status.rssi` 有新鲜值时才显示“发现”；因此会先显示等待/未发现。现在即使还没有进入可信测距，也会记录 `SCAN_FOUND` 和 `WAKE_REQUEST` 轨迹，顶部可以立即显示“发现车辆，正在唤醒银河”。

## 4. 行为边界

- 轨迹是观测记录，不改变扫描、连接、鉴权或车控判定；
- 轨迹不替代 `PASSIVEKEY` 日志，也不把 `SENT` 写成车辆执行成功；
- 轨迹保留最多 8 条，避免服务长时间运行时无限积累；
- 切换到新唤醒会话、重学车辆、重新启用服务或主开关重建时清空旧轨迹；
- 轨迹同时写入导出快照 `live_trace=...`，便于把界面显示和日志对照。

## 5. 回归

`LiveActivityTest` 新增覆盖：

1. 发现→唤醒→ACL→鉴权→请求→发送的短阶段轨迹；
2. 顶部优先显示最近可解释阶段而不是静态“等待”；
3. 超过 30 秒的旧轨迹不冒充当前动作；
4. 轨迹文本保留最近四步并限长。
