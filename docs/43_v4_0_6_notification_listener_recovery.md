# 43. v4.0.6：通知监听掉绑诊断、重绑请求与一键修复

版本：`4.0.6-min / versionCode 106`。保留v4.0.5手动测试按钮、默认距离参数`-75 / -82 dBm / 4.5s`和既有车控状态机，本次只处理通知监听生命周期与已有通知补扫。

## 1. 实机现象与证据

用户反馈v4.0.5在银河App已连接蓝牙钥匙时仍显示“等待银河就绪”，手动解锁提示“通知监听尚未就绪”；v4.0.3没有该问题。

2026-11-09本机日志与系统状态：

- 20:18:11`KeyNotificationBridgeService`曾成功连接，20:18:12读到银河通知，`unlock_button=PI`、`lock_button=PI`，并成功发送一次解锁。
- 20:30:12进程被系统以`LOW_MEMORY`原因杀掉；20:30:13前台服务重建后，`notification_access=true`，但`listener_connected=false`。
- 20:30至20:52，本应用每分钟调用`NotificationListenerService.requestRebind()`，持续22分钟都没有重新绑定。
- 系统`dumpsys notification`仍把本应用列在`Allowed notification listeners`和`All notification listeners enabled`，但不在`Live notification listeners`。
- 系统通知列表里银河`com.geelygalaxy.customer id=5`通知一直存在。因此不是银河未连接，也不是通知使用权丢失，而是监听实例没有恢复。
- 20:52使用系统`cmd notification disallow_listener`再`allow_listener`后，监听立即回到Live列表；20:54覆盖安装后也能正常绑定并补扫银河通知。
- 20:57再次覆盖安装后，监听没有自动绑定。应用在2秒、4秒、8秒、10秒持续发起`requestRebind()`仍无效。
- 20:57验证应用自身切换组件启用态不会触发重绑；20:58~20:59验证系统切换组件启用态和切换无害`BootReceiver`也不会触发重绑。
- 测试中发现：直接禁用`KeyNotificationBridgeService`会让系统按组件变更杀掉整个应用进程，因此该方案不能用于线上自动恢复。
- 21:02安装`4.0.6-min / 106`后，应用进程启动时监听仍未绑定；执行系统通知授权关闭再开启后，`Live notification listeners`重新包含本应用，应用日志出现`listener_connected=true`、`notification_present=true`、`notification_parse=PUBLIC_OK`。
- 21:03再次覆盖安装后，系统监听自动恢复在线；界面显示“已授权 · 监听在线”，“修复通知监听”按钮可见。应用成功读取银河常驻通知，说明监听与补扫链路正常；银河通知当前没有暴露解锁/上锁按钮，官方连接状态仍以银河App自身为准。

结论：

1. vivo Android 16在该机型上，进程被低内存杀掉或覆盖安装后，公开`requestRebind()`可能长期无效。
2. 系统通知使用权列表中的“已允许”只代表授权存在，不代表监听实例已经绑定。
3. 第三方应用没有可用的公开接口去代替用户重新授予通知使用权；可用且可靠的恢复动作是用户在系统页关闭再开启一次本应用的通知使用权。
4. 监听刚绑定时`getActiveNotifications()`存在空列表竞态，原代码只扫描一次会一直漏掉已经存在的银河通知。

## 2. 修复

### 2.1 重绑请求与明确状态

`PassiveKeyService`每2秒检查通知监听：

- 监听已授权且已连接：清除掉绑状态，定期补扫缺失的银河通知。
- 已授权但未连接：每2秒节流调用一次`requestRebind()`，不修改组件启用状态，不杀应用。
- 连续10秒仍未连接：状态标记为`listener_recovery=needs_user_access_toggle`，界面明确显示“已授权 · 系统未绑定”，不再把系统授权误显示为可用。

### 2.2 一键修复入口

权限卡新增“修复通知监听”按钮，直接打开`ACTION_NOTIFICATION_LISTENER_DETAIL_SETTINGS`并定位到本应用组件；不支持详情页的ROM回退到通知使用权列表。

用户只需在系统页把本应用的通知使用权关闭再开启，系统会重新绑定监听。手动按钮检测到掉绑时也会提示使用该入口；导出日志记录`LISTENER_DOWN`和`needs_user_access_toggle`。

同时前台常驻通知会从“等待银河蓝牙连接”改为“通知监听被系统解绑 · 点此打开App修复”，避免后台故障静默不可见。

### 2.3 已有通知补扫

监听连接后除立即扫描和800毫秒后补扫外，监听已连接但尚未读到银河通知时每1.5秒重扫一次现有通知。读到后停止高频扫描；银河通知真正移除时仍由原有移除回调清理按钮。

补扫复用原有`NotificationEpoch`版本控制，不绕过通知版本、旧解析和移除事件隔离。

### 2.4 安装脚本

`build.sh`在真机安装后保留原有`cmd notification disallow_listener` / `allow_listener`步骤，用于系统安装或覆盖安装后的首次重绑。普通APK安装若遇到系统未绑定，使用App内“修复通知监听”。

## 3. 安全边界

- 不自动修改通知使用权；只在用户点击“修复通知监听”时打开系统页。
- 不再禁用/启用监听组件，避免杀掉应用进程或留下不可用组件。
- 不对银河App做force-stop、清数据、改设置或读取私有数据。
- 恢复检查复用已有500毫秒服务tick并节流到2秒，不新增后台轮询线程。
- 车控发送前仍复核服务总开关、插线禁控、行驶状态、官方连接和按钮是否可用。

## 4. 验证

- 七组既有测试、资源编译、Java编译、DEX和签名均通过。
- 覆盖安装后确认系统Allowed列表保留本应用；服务启动后监听可在线；`notification_present=true`；银河通知按钮可解析。21:02/21:03实机已确认“修复通知监听”按钮出现在权限卡中，监听恢复后界面显示“已授权 · 监听在线”。
