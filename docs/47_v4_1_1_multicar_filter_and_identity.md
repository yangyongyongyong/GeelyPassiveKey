# 47. v4.1.1：多车过滤、可信身份与单目标测距

版本：`4.1.1-min / versionCode 111`。2026-11-12 本地修改与构建；当日随后已在用户明确授权下安装到vivo手机并恢复配置，未发布到GitHub。v4.1.2只增加版本显示/命名，见文档48。

## 1. 结论与证据边界

用户实测附近只有一辆车时快，多辆尤其吉利系列时慢。v4.0.9源码确定存在三个缺陷：

1. 已学习后仍保留 `0x01FE/0x06FE/FDFD` 宽过滤，只追加本车名称与MAC；过滤列表是OR，范围没有收窄。
2. 匿名广播可仅凭VIN后两位命中本车，`mergeWith`直接覆盖MAC；同MAC判断先于冲突车名，污染后可继续把其他车名合入身份；已学习分支没有单目标RSSI隔离。
3. 第一包广播时 `candidates.size()==1` 就可能记住第一辆；所谓12秒主候选实际是“最后一次广播后12秒”，持续广播不会超时。

这些路径已经用原始匹配/选择/滤波代码离线复现，但**不等于已经证明昨天停车场的根因**。手机v4.0.9与本地APK SHA-256一致；保留日志的09:40会话从首广告到指令交付15.095秒，其中官方已连接后等待RSSI阈值9.778秒（`FRESH_FAR_SIGNAL -86 dBm`，后续到`-73.6 dBm`才发送）；12:49会话4.657秒且官方就绪后立即交付。昨天日志及09:40采样明细已轮转，不能区分实际距离、遮挡、多径与身份混流。

本次修复不降低`-75/-82 dBm`阈值、不取消远场/行驶/插线保护，不承诺所有多车或射频干扰场景都变快。

## 2. 过滤模式：替换宽规则，而不是追加精确条件

`VehicleScanPolicy`生成同一份可测试计划，`PassiveKeyService`直接转换成Android `ScanFilter`：

| 模式 | 规则 | 边界 |
| --- | --- | --- |
| `LEARNING` | `0x01FE/0x06FE/0xFF15`厂商ID、`0xFDFD`服务UUID | 仅首次无任何匹配提示；列表非空，保持息屏扫描 |
| `HINT_DISCOVERY` | 精确尾号设备名、已有完整厂商前缀，或vendor+VIN位掩码 | 手填尾号不是已验证地址，不参与车控 |
| `TRACKING` | 已学习MAC、精确名称、已观察到的完整厂商前缀 | **没有裸Company ID或UUID规则**；名称/前缀保留MAC轮换发现能力 |

厂商前缀一般含vendor/version/固定位/VIN后两位，不是车辆全局唯一ID。即使硬件放行相同前缀的匿名邻车，软件也只给它发现资格，不直接测距或更新身份。只有MAC证据且无名称/前缀的旧配置，仅跟踪该MAC；匿名地址轮换又没有任何身份依据时，需要官方真实连接证据或重新学习，不能靠无限广扫和盲绑定兜底。

重建过滤延迟750ms合并；全进程共享最多4次/30秒、至少1秒间隔预算。预算不足时保留原扫描并延后重配置，不先stop造成空窗；用户主动关闭服务仍立即停止。旧息屏看门狗沿用，但同样受启动预算约束。

## 3. 身份分级与RSSI门控

- `CONFLICT`：明确不同车名或尾号；先于MAC命中拒绝。
- `ADDRESS`：已验证地址相同，可用于单目标RSSI。
- `NAME`：完整`GeelyVehicle`尾号名称命中；旧MAC停更超过3秒、新MAC至少2条同名广告且跨600ms、官方尚未连接时，才选择唯一发现候选。名称末三位也可能重名，跨MAC仍不直接测距或更新地址，真实连接确认后才采用。
- `HINT`：匿名后两位/完整短前缀一致，或者手填尾号提示；**只能找车并把新鲜广告交给官方鉴权，不改MAC、不计RSSI、不生成自动车控**。
- `NONE`：没有可用身份依据，拒绝。

同MAC的ScanResponse名称补全不会制造第二个候选。已观察到的近期冲突车名，不会被下一条无名广告擦除。同MAC普通缓存名称也不会抹掉已学习的吉利名称。

`mergeWith`只接受已验证同MAC补全；不同MAC的名称/尾号/短前缀均不能自行覆盖地址/签名。已学习和未学习路径共用`VehicleTargetSelector`，不能不同匹配分支分别喂入同一滤波器。官方连接中固定已验证目标；广播停发时不会被另一辆同名或同尾号车抢测距源。

物理测距目标变化时重建RSSI滤波、清旧驻留和距离证据；旧待发动作统一取消，但保留已交付动作和手动上锁锁存，避免换地址又自动重复解锁。广播滤波和状态机采用扫描的实际采集时间，不用Handler处理时间伪造新样本；原始纳秒去重允许同毫秒ScanResponse补名，定时维护不会把同一广告反复计为新的RSSI样本。测距授权在选择器的同一方法中集中检查，测试与服务共用。

## 4. 首次学习与匿名MAC轮换

第一包只能进入观察，不再直接永久学习。物理地址按原始纳秒时间去重，毫秒内ScanResponse可补名；至少观察1.5秒/至少2个新时间戳，再尝试唯一主候选。未知候选预算从选中时刻起算12秒，持续广播不会续期；失败MAC进入30秒冷却，期间短暂消失/重现也不重置冷却，其他新鲜候选有机会尝试。

完成学习条件：

1. 官方通知明确已连接；
2. 系统GATT列表及本应用已有GATT按地址去重后只有一个符合身份的可验证设备；
3. 有精确名称或同MAC近期广播证据，且与手填/已学习车名、尾号不冲突。

这是“官方就绪 + 系统唯一匹配连接”的交叉证据，不宣称能读取系统连接属于哪个App的私有归属。多个匹配连接、匿名无证据、通知在线但地址不可见时不猜测绑定；不再拿`lastWakeAd`推断“官方一定连的是它”。ACL在官方就绪之前只记录握手事实，不完成车辆学习。可信地址证据比官方通知晚到时，会补处理本次连接的一次就绪机会；不能伪造第二个连接边沿，也不撤销近场/远场、行驶和插线保护。

匿名轮换地址必须经过上述连接确认。手填后三位在连接名缺失时继续保留，不能被只有两位尾号的广告降级。更换车辆提示不继承旧MAC；清空学习不重置用户阈值和自动开关。

候选容量最多32个物理MAC，保留20秒，定时清理；无广播时的快照也不会把历史候选算作“附近多辆车”。

## 5. 结构与兼容性

| 文件 | 职责 |
| --- | --- |
| `VehicleBeacon.java` | 纯Java公开字段与解析；校验vendor、精确车名及尾号一致性，短前缀编码 |
| `GeelyAdvertisement.java` | Android `ScanRecord/ScanResult`包装；厂商AD结构读取和采集时间 |
| `VehicleIdentity.java` | 强/弱身份、冲突优先、连接交叉证据、受保护的合并 |
| `VehicleTargetSelector.java` | 物理地址候选、单目标门控、轮换观察、未知预算与冷却 |
| `VehicleScanPolicy.java` | 学习/发现/跟踪计划，厂商掩码及全进程扫描启动预算 |
| `OfficialReadyGate.java` | 官方通知先到/地址晚到时每次真实连接只处理一次就绪机会 |
| `PassiveKeyService.java` | 统一应用计划、匹配/连接学习、可信RSSI、日志与节流 |

新增`vehicle_manufacturer_id`偏好，旧版六字节01FE及八字节15FF布局可迁移；厂商签名损坏时不生成错误过滤。原开关、阈值、通知授权和签名密钥不重置。

解析器不再在原始字节串中搜索`15FF`，而是使用`ScanRecord`已拆分的对应厂商字段，避免普通负载巧合出现子串被当车辆。未知匿名15FF载荷缺乏可识别vendor/version时不盲认；有精确吉利名称的兼容路径仍保留。`GeelyVehicle`名称接受两到三位字母/数字尾号，公共前缀及类似音箱名称拒绝。

## 6. 日志与验证

新增`filter_mode`、`MATCH_RESULT`、`TARGET_SWITCH`、`IDENTITY_UPDATED`、`CONNECTED_IDENTITY`、真实采集时间/回调年龄、`scan_discovery_only`和候选预算年龄。拒绝包不逐包落盘，匹配详情每5秒最多一条；地址、名称、厂商前缀只记录加盐指纹，不导出原始广播、完整VIN或钥匙凭证。

## 7. 实车验收

在允许安装后沿用原签名覆盖，不卸载、不清数据。保持原阈值，用以下场景测试并及时导出ZIP：

1. 已学习本车，停车场只有一辆：首广播不新增观察等待，官方就绪到交付仍及时。
2. 多辆吉利相邻：跟踪模式无宽过滤；其他匿名包只出现`HINT/DISCOVERY`，不能改变本车MAC或RSSI。
3. 本车MAC轮换且名称可见：旧目标停更、新名确认后单目标切换，不反复跳地址。
4. 只见匿名轮换：官方连上且系统匹配连接唯一后更新地址，不凭同尾号提前绑定。
5. 锁屏放口袋、打开/关闭总开关、掉绑恢复；关闭必须停止全部自动请求。
6. 手动上锁后仍站车旁、行驶中及插线供电：修复不能解除这些安全保护。

记录“首目标广告→官方已连接→请求→交付”各阶段；交付仍不等于车锁执行回执。附近车辆数及实际站位/遮挡由测试者标记，不能用候选数代替。

## 9. v4.1.4 后续：预连接和可信测距分离

上面的600ms名称确认/1.5秒匿名观察继续用于**普通主候选选择**，不再作为所有首包预连接的前置条件。已保存本车MAC/完整名称，且当前真实扫描包同时具有完整本车名及一致Company/vendor/VIN尾号时，可由独立`VehicleWakeGate`先向官方尝试连接；厂商中间状态/版本字段允许变化，匿名HINT、缓存设备名、仅手填提示均保持原路径。

这不是恢复同品牌宽扫描或把新MAC首包当可信本车：`VehicleIdentity`、硬件扫描计划、RSSI授权、上锁状态机和单队列发送代码未改。普通选择与预连接共用十二秒尝试起点和三十秒冷却，只允许一个未知在途目标；目标确认不重置同地址节流或ACL握手保护，真正已验证的MAC没有ACL阻碍时可以优先恢复。身份保存仍依赖唯一可验证的实际连接。首包快路径新增物理连接待验证门控，不能凭旧学习MAC把提前到达的官方通知当作新连接身份验证；验证采用后继续就绪/车控/挂载，原已学MAC会话不受此守卫影响。

新增`CANDIDATE_FIRST_SEEN`、命名观测/跨度/重置原因、`WAKE_REQUEST phase`与`WAKE_WAIT`，避免旧`TARGET_FIRST_SEEN`隐藏选择前等待。三份实车日志证据、合成回归及未验证的3–5米目标见 [50_v4_1_4_early_connection_latency.md](50_v4_1_4_early_connection_latency.md)。

## 10. v4.1.5 后续：厂商发现从六字节全等改为稳定VIN掩码

v4.1.1当时为了缩短多车过滤，跟踪计划使用“已观察到的完整厂商前缀”逐位全等；v4.1.4仍受这个边界影响。实车同车的version、devices等字节会变化，导致系统`ScanFilter`在回调前丢弃广播。v4.1.5按官方V2历史实现的稳定位改写：

- 优先规则：`FF 00 FF 00 FF FF`，匹配`vendor + antenna + VIN后两位`；
- 兜底规则：`FF 00 00 00 FF FF`，匹配`vendor + VIN后两位`，只在antenna也可能变化时放宽该位；
- Company ID仍严格一致，完整名称、VIN冲突和已学习MAC规则继续优先；
- 稳定掩码命中的跨MAC广播仍是`HINT`，不改地址、不供RSSI、不触发自动车控；
- 匿名HINT仍需2条、1500ms观察，不能走首包`SEND_EARLY_NAME`；实际连接验证后才可能更新身份；
- 不恢复裸Company ID/UUID宽扫，不改变4.1.4的预连接、ACL保护和上锁状态机。

v4.1.1文档第2、3节里的“完整厂商前缀”表述是历史状态；当前代码以[52_v4_1_5_stable_mask_discovery.md](52_v4_1_5_stable_mask_discovery.md)为准。
